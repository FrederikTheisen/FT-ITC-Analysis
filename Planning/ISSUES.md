# Issue tracker

Resolved, completed, and closed entries retain Status, Problem, and Resolution, including useful code references, limitations, and linked follow-ups; completed plans and execution logs are omitted.

## ITC-001 — Asymmetric rounding of negative display values

- Status: Resolved (2026-10-02).
- Problem: `FWEMath.RoundApproximate` rounded −2.5 to −2 but +2.5 to +3; its digits overload also rounded −2.6 to −2. The asymmetry affected Standard/Strict displayed estimates and interval endpoints.
- Resolution: Both overloads use sign-symmetric midpoint tolerance based on the original value and apply the requested midpoint mode to the scaled value. Independent Core cases cover mirrored signs, tolerance margins, negative digits, non-finite inputs, and formatted output.

## ITC-002 — Expanded bounds on logarithmic affinity coordinates

- Status: Resolved (2026-10-02).
- Problem: `Parameter.RefreshLimits` multiplied log₁₀K bounds directly: Extended produced [−40, 400] and No limit [−4000, 40000], allowing affinity overflow/underflow and infinite derived ΔG despite finite model predictions.
- Resolution: Widen physical K bounds by factors of 20 or 2000 using additive log₁₀ factors; negative log₁₀K remains allowed. Reject global candidates when affinity or linked enthalpy coordinates yield non-positive or non-finite K/Kd, while allowing finite affinities outside local presets. Focused tests cover physical endpoints, overflow/underflow, and locked coordinates.

## ITC-003 — pKa correction can fail to converge

- Status: Resolved (2026-10-03).
- Problem: Buffer pKa fixed-point correction could cycle; phosphate at pH 8.198, 25 °C, and 5 M reproduced non-convergence.
- Resolution: `Buffers.cs` solves the existing ionic-strength balance by bounded bisection, returning NaN for invalid inputs or an unverifiable finite solution after 128 iterations. The nearest-pKa/two-species approximation and monovalent-counterion assumption remain; numerical convergence does not establish high-concentration chemical accuracy. Solution-wide correction is deferred under ITC-027.

## ITC-007 — Avalonia UI tests fail when certain test classes run together

- Priority: Medium
- Status: Resolved (2026-10-10).
- Location: `AnalysisITC.Avalonia.Tests`, the `[Collection("Avalonia UI")]` classes, `AvaloniaTestApplication.cs`, and `AvaloniaDispatcherTests.cs`.
- Problem: The headless platform is set up once with `SetupWithoutStarting`, which binds Avalonia's UI thread to whichever xUnit worker thread runs first. xUnit does not guarantee that later tests in the collection run on that thread. When the thread changes, every following test that creates a window fails with "The calling thread cannot access this object because a different thread owns it", in a cascade unrelated to the code under test.
- Reproduction (2026-10-01): `PreferencesTests` alone passes (24/24), but run together with `ExperimentDetailsWindowTests`, `AnalysisReportRenderingTests`, or `ExperimentIdentifiersWindowTests`, about 18 tests fail, starting with the test after `SavedAccessSurvivesOpeningApplyingAndReopeningPreferences`. `PreferencesTests` on its own also failed this way once in three runs.
- Review verification (2026-10-06): The full Release Avalonia suite again produced the same cross-thread exception cascade and stopped making progress; the review run was interrupted. Separately filtered runs exposed deterministic stale assertions, tracked in ITC-065, so those failures should not be attributed to this threading issue.
- Reproduction (2026-10-08): `PreferencesTests` alone now fails in most runs. Three alternating runs with and without the ITC-080 date changes gave the same pattern (without: 24/24, 18 failed, 19 failed; with: 19, 18, 19 failed), every failure the cross-thread exception, so ITC-080 is not the cause. Some runs hang instead: the blame collector stopped one at `PublicationFontRoundTripsAndShowsResolvedFamily`, and a stalled test host had its main thread blocked in a monitor wait, consistent with `Dispatcher.UIThread.Invoke` waiting for a dispatcher loop that `SetupWithoutStarting` never runs.
- Investigation (2026-10-10): Current Release tests reproduce the ownership failure both with the four originally reported classes (51 passed, 19 failed) and with `PreferencesTests` alone (5 passed, 19 failed). All failures have the same cross-thread exception; both runs first fail at the `advanced` case of `SavedAccessSurvivesOpeningApplyingAndReopeningPreferences`, after its other two cases pass. A control run of the other three classes plus the previously failing `RegistrationButtonShowsUntilAccessIsVerified` passes all 47 tests. These runs complete without hanging. The collection currently spans 46 classes and 248 fact/theory declarations, including five async test methods, so correcting only Preferences would leave the same infrastructure defect elsewhere.
- Consequence: Full or filtered Avalonia runs can report failures that are not regressions; a real failure can be hidden among them.
- Resolution: Migrated only the Avalonia test project to xUnit v3 and [`Avalonia.Headless.XUnit` 12.0.5](https://www.nuget.org/packages/Avalonia.Headless.XUnit/12.0.5), converted all 248 existing UI fact/theory declarations to Avalonia attributes, and removed the worker-thread bootstrap. The supported runner dispatches construction, execution, async continuations, and cleanup on its owned UI thread. Explicit per-assembly isolation preserves the existing shared application, and the UI collection remains serial for shared Core settings and document state. Added three async theory cases covering constructor/cleanup access, resuming after an await, and serving a synchronous UI dispatch from a worker while the test awaits it. The Preferences tab test now establishes and restores its session state instead of assuming that no earlier test selected a tab. No application or scientific code changed.
- Validation: All 73 focused Release tests pass, followed by three additional successful 73-test reproduction runs. The full Release suite completes in six seconds with 360 passed and six failed, with no UI-thread ownership exceptions or hangs. All six remaining failures are in `AnalysisReportEnhancementTests`, reaching `ProcessingClearPlan.Entry` through a retained MainWindow menu subscription and throwing "Max must be greater than or equal to min" for its sparse fixture's default injection delays. That class passes all 14 tests in isolation; this separate suite-state/processing-clear interaction is not resolved by ITC-007 and is tracked as ITC-101. `git diff --check` passes for the changed test files.

## ITC-008 — Null Offset labels can expose unmatched experiment IDs

- Priority: Low (reassessed 2026-10-02; original High-priority unit defect resolved in the current working tree).
- Status: Partially resolved; ID-label fallback remains open.
- Location: Shared `NullModelComparisonPresentation.FormatNullParameters` (`AnalysisITC.Core/Presentation/NullModelComparisonPresentation.cs`), called by `AnalysisResultTableExporter`, `Exporter` and `AnalysisReportBuilder`. - Recheck (2026-10-12): The fallback is still present in the shared formatter: an unmatched member without a report label uses the result's solution name or, failing that, `member.ExperimentId`, independent of Traceability Mode.
- Reassessment: The Offset is heat per mole of injectant, stored in J/mol. Both paths now resolve the selected energy family/override and call `Energy.ToString(unit, "G6", withunit: true, permole: true)`, which correctly converts the value and includes the molar unit. The original raw-value "µJ" export and unitless report defects are no longer present. Normal exports use experiment names; no-binding reports use report labels such as `1A`. `ToFormattedString` is not necessary to correct the units; the current `ToString` overload also performs the conversion.
- Remaining problem: Both formatters fall back to `member.ExperimentId` when the saved comparison member cannot be matched to an experiment name or report label. That fallback is not gated by Traceability Mode. A constructed unmatched-member case reproduces the ID exposure with Traceability Mode disabled; this is a defensive label-handling edge case, not a reproduced error in normal matched results.
- Validation (2026-10-02): 123 targeted Core checks passed, including seven temporary reassessment probes. For −10536 J/mol, both outputs produced −10.536 kJ/mol (automatic Joules) and −2.51816 kcal/mol (automatic Calories); explicit J, kJ, cal, and kcal overrides also passed independent expected-value checks. Normal name/report labels and the unmatched-ID fallback were verified. The temporary probes were removed after reassessment; production code was not changed.
- Follow-up: Use a readable fallback label when a saved comparison member cannot be matched; show internal IDs only under Traceability Mode. Add lasting regression coverage for null-offset unit conversion and matched/unmatched member labels when implementing that follow-up.

## ITC-014 — Assessment labels now drive which parameters are hidden

- Status: Resolved (2026-10-05).
- Problem: Assessment cutoffs and their output restrictions needed a consistent policy, especially for Inconclusive results and manual overrides.
- Resolution: Rule `aicc-0-10-v1` assigns No binding detected at signed ΔAICc ≤ 0, Inconclusive at 0 < ΔAICc < 10, and Binding detected at ΔAICc ≥ 10. Saved outcomes/rule IDs restore unchanged. Inconclusive retains binding output/uncertainty and adds a health warning without changing input validity; manual overrides are authoritative. Combined binding output requires every member to be eligible, without subset recombination. These chosen cutoffs have no calibrated false-positive guarantee and do not exclude varying dilution heat, buffer mismatch, or drift. Later Standard report suppression is recorded in ITC-051; Standard table exports omit no-binding values.
- Follow-up (2026-10-10): Rule `aicc-0-15-v1` raises the Binding detected cutoff to ΔAICc ≥ 15; the Inconclusive interval is now 0 < ΔAICc < 15, with No binding detected still at ΔAICc ≤ 0. New fits and refits use this rule. Saved assessments under earlier rules and manual overrides retain their recorded outcomes.
- Follow-up (2026-10-12): Load-time reevaluation supersedes the historical-outcome preservation above. The reader recalculates the automatic assessment from saved comparison evidence using the current rule, regardless of the saved rule ID, and retains manual overrides, fitted values, and stored uncertainty. It does not refit on load or introduce historical-rule evaluators or new persistence fields.

Reuse the linked evaluator where applicable, decide profile-likelihood treatment explicitly, and route affected UI/report/export consumers through the agreed shared evaluation. Do not change generic `FloatWithError` subtraction to assume an unknown correlation. This is a design direction, not implementation approval or a separate issue.
- Agreed constraints: Preserve original best-fit centers. Zero error means the error does not exist; do not invent additional error tracking. Preserve the current CR-024/SUMMARY_SEM summary convention unless a change is explicitly reviewed. Keep CR-010's failed-profile safeguards and ITC-114 primary-fit recovery separate.

Interpretation evidence emits `salt-dependence-slope` and explicit logarithmic axes; every active scientific/summary guidance variant distinguishes this slope from an ion count. Manual, in-app help, report map, format/schema documentation and scientific-validation notes are aligned.

Version 1 (including the historical missing-version default) retains primary fits, ionic-strength output, other advanced analyses and report text, while omitting the obsolete slope and its sampling count. ## ITC-217 - A single retained refit gives an interval without an SD

- Priority: Not set.
- Status: Open (2026-10-23). Source review only; no fix proposed or authorized.
- Origin: ITC-117 plan review, while discussing its proposed single-refit rule for derived quantities.
- Location: Core `Math/NumberStructs.cs` (`FloatWithError.FromDistributionInPlace`, `HasError`, `HasConfidenceInterval`, `ResolveDisplayStyle`, `FormatNumberWithUncertainty`); `Analysis2/Models/Models.cs` (`SummarizeBootstrapDistribution`); `Analysis2/Models/ThermodynamicSolution.cs` (`BootstrapEstimate`); `Analysis2/Solver2.cs` (`GlobalSolver.LeaveOneOut`); `Analysis2/GlobalModel.cs` (`LeaveOneOut`, `SetBootstrapSolutions`).
- Problem: With exactly one retained refit, `FromDistributionInPlace` sets the SD to 0, because the SD needs at least two values (`NumberStructs.cs:105`), but sets both interval bounds to that refit's value (`NumberStructs.cs:115`). The result has a one-point interval and no SD. Unless the refit equals the primary fit, the interval does not contain the reported best-fit value. Fitted coordinates reach this through `SummarizeBootstrapDistribution` (`Models.cs:898`), called from `ThermodynamicSolution.BootstrapEstimate` (`ThermodynamicSolution.cs:65`).
- Display consequence: The formatter tests the SD (`HasError`, `NumberStructs.cs:42`) and the interval (`HasConfidenceInterval`, `NumberStructs.cs:494`) separately. With Automatic display, the asymmetry score is undefined because one side of the interval has non-positive width (`NumberStructs.cs:218`), so SD display is chosen and nothing is shown. With Confidence interval or SD and CI display, or a caller that requests the interval, the one-point interval is printed next to the best-fit value.
- Routine trigger: Global leave-one-out leaves out a whole experiment per refit (`Solver2.cs:1946`, `GlobalModel.cs:276`), and each member receives only the refits it took part in (`GlobalModel.cs:774-776`). In a two-experiment global fit, each member therefore has exactly one refit: the one that left out the other experiment. Every value summarized from that member's refits is affected, including the member's copies of shared coordinates. Whether any consumer shows shared coordinates from the global-level refits instead was not traced. Other triggers: a bootstrap or leave-one-out run in which all but one refit fail for a member.
- Scope found: This is the only path found that produces a displayed interval without an SD. Profile results derive the SD from a complete interval and give neither when the interval is incomplete (`ProfileLikelihoodResult.cs:146,158`). Summaries of two or more refits have a nonzero SD whenever an interval bound differs from the best fit. Arithmetic and transforms propagate the SD and interval widths together, so derived values only inherit the problem from an affected input.
- Not checked: Integrated-heat refit envelopes use the same summarizer per injection (`Models.cs:228-277`), so with one refit the envelope would sit on that refit's prediction; its rendering was not checked. Exports and other consumers that read the bounds directly were not traced.
- Related: [ITC-117](#itc-117---derived-parameter-uncertainty-across-all-models) proposes a local single-refit rule for derived quantities (best-fit value, zero SD, interval collapsed onto the best fit). Fitted coordinates would keep the behavior described here, so fitted and derived values would differ for the same evidence.
- Evidence: Source review only (2026-10-23); no build, test, runtime reproduction, UI or export check was performed.

## ITC-218 - Bootstrap restoration still reads and writes the stored model options

- Priority: Not set.
- Status: Open (2026-10-23). Source review and instrumented timing only; the suspected effect has not been reproduced. No fix proposed or authorized.
- Origin: ITC-216 investigation.
- Location: Core `Analysis2/BootstrapModelSnapshot.cs` (`Restore`, which calls `SingleModelFactory.InitializeModel`); `Analysis2/ModelFactory.cs` (`InitializeModel` option recovery, `SetModelOption`, `StorePreviousAttribute`). Primary solutions are restored differently, in `DataReaders/FTXTCReader.cs` (`RestoreSolutions`: `FtxtcModelRegistry.Create` and `InitializeParameters`).
- Problem: Each restored replicate model is built with `SingleModelFactory.InitializeModel`. This copies every option present in the static `ModelFactory.PreviousAttributes` into the model, stores a copy back in the list, and applies the options before `Restore` installs the snapshot's own options. Snapshot options replace only the keys the snapshot contains. ITC-082 kept this shared memory for non-designer factories because these paths apply their saved options afterwards; that holds only for keys present in the snapshot.
- Hypothesis (untested): A replicate snapshot without an option key, for example from a file saved before that option existed, would keep the session's last-used value, while the primary fit restored from the same file gets the catalog default. The replicate's predictions, bands and uncertainty could then depend on what was done earlier in the session. In a fresh process, and in the web viewer (where nothing writes the list), the list is empty and there is no effect. Whether any saved bootstrap snapshot lacks an option key, and whether reading fills in missing keys, was not checked. The other reconstruction paths named in ITC-082 were not re-examined.
- Side effect: Restoration rewrites the static list (removing and re-adding each recovered key) while a project is read. Thread safety relative to UI code that reads or writes the list was not checked.
- Cost: The recovery step and its first `ApplyModelOptions` took 12 ms and 4.7 MiB for 13,000 replicates in `JORS Table1.ftxtc`. This is a consistency question, not a performance one.
- Related: [ITC-082](#itc-082---model-options-leak-between-the-experiment-designer-and-analysis), [ITC-216](#itc-216---restored-bootstrap-replicates-dominate-project-load-memory).
- Evidence: Source review and instrumented timing on a copied Core (2026-10-23); no reproduction with a populated list or an older file. Evidence directory as for ITC-216.

## ITC-219 - Global replicate restoration and saving rescan member replicate lists

- Priority: Not set.
- Status: Open (2026-10-23). Measured on one fixture; no fix proposed or authorized.
- Origin: ITC-216 investigation.
- Location: Core `DataReaders/FTXTCReader.cs` (`RestoreResults`, global replicate loop: `BootstrapSolutions.SingleOrDefault(... BootstrapReplicateIndex == replicate.Index)` per member); `DataExport/FTXTCFormat.cs` (`CaptureGlobalReplicates`: `BootstrapSolutions.Select(...).Contains(index)` per member).
- Problem: For each saved global replicate, restoration finds each member's replicate by scanning that member's whole bootstrap list, and saving checks membership the same way. The work therefore grows with members × replicates² per result. The reconstruction path in `GlobalSolution` already indexes replicates in a dictionary.
- Measurement: `JORS Table1.ftxtc` (8 results, 13 member fits, 1,000 replicates each): the restoration lookup took 75 ms in total, about 6 ns per comparison. Save-side time was not separated.
- Estimate (not measured): At the same cost per comparison, a 2-member result with 10,000 replicates per fit would spend about 1.2 s in the lookup on load, and a single fit with 20,000 replicates about 2.3 s; saving would be similar. The desktop applications have no replicate cap, so larger ensembles grow quadratically.
- Constraint: Any change must keep pairing by replicate index, and a missing member replicate must still not shift later pairings.
- Related: [ITC-216](#itc-216---restored-bootstrap-replicates-dominate-project-load-memory).
- Evidence: Instrumented timing on a copied Core (2026-10-23). Evidence directory as for ITC-216.

## ITC-220 - Interpretation baseline diagnostics rescan the thermogram for every injection

- Priority: Not set.
- Status: Open (2026-10-23). Source review and one sampled profile; no fix proposed or authorized.
- Origin: ITC-216 investigation (load-time profile).
- Location: Core `Interpretation/AnalysisInterpretationDiagnostics.cs` (`AddInjectionBaseline`, `Integrate`, `Interpolate`), called from `AnalysisInterpretationPackageBuilder.BuildExperiment` for every integrated injection. Project loading reaches it through `AnalysisInterpretationService.EvaluateFreshness` for each saved report with an approved automatic interpretation.
- Problem: For each injection, `AddInjectionBaseline` builds and sorts a list pairing every thermogram sample with its baseline value. `Integrate` then interpolates at every sample inside the integration window, and each interpolation finds its position with a linear `FindIndex` from the start of the list. Per experiment, the work grows with injections × samples for the sorting plus window samples × samples for the interpolation.
- Measurement: In a cold load of `JORS Table1.ftxtc` (two saved reports), freshness evaluation took about 1.8 s and 206–210 MiB of allocation. A sampled thread-time profile (one run, with the ITC-216 metadata-cache prototype) attributed about 0.95 s to `AddInjectionBaseline` and about 0.6 s to bootstrap bands. The web viewer pays the same cost because it reads projects through the same loader.
- Constraint: The diagnostic values belong to the interpretation package that is fingerprinted for freshness. Any change must keep them bit-identical, or approved interpretations may be reported as stale.
- Not checked: Warm (JIT-compiled) cost, other projects, and other callers of the package builder.
- Related: [ITC-216](#itc-216---restored-bootstrap-replicates-dominate-project-load-memory).
- Evidence: dotnet-trace sampled profile and source review (2026-10-23). Evidence directory as for ITC-216.

## ITC-221 - Reopening and saving regenerates embedded Null-comparison solution ids

- Priority: Not set.
- Status: Open (2026-10-23). Observed in saved packages; consequence not assessed. No fix proposed or authorized.
- Origin: ITC-216 investigation (comparison of re-saved packages).
- Location: Core `DataReaders/FTXTCReader.cs` (`RestoreOffsetSolution` creates the detached Offset solution through `SolutionInterface.FromModel` and does not restore the saved id); `DataExport/FTXTCFormat.cs` (Null-comparison capture writes the solution's current id).
- Problem: Each Null-comparison member embeds an Offset solution with an `id`. Restoration builds that solution with a new GUID and ignores the saved one, so every load and save writes new ids. - Related: [ITC-148](#itc-148---reopening-changes-the-embedded-null-solutions-heat-method-provenance) (another reopen/resave change in the same embedded solution).
